# Trade architecture

## Components

```text
Android app
    |
    | HTTPS + app bearer token
    v
cPanel / PHP API
    |
    +--> RiskManager --> OrderService --> BitpinClient --> Bitpin API
    |
    +--> MySQL: orders, trades, strategies, signals, audit logs
    |
    +--> Cron tick: scheduled strategy / reconciliation work
```

## Boundary rules

1. Android never receives the Bitpin API secret.
2. Bitpin credentials are encrypted using a random 256-bit application key generated by the installer.
3. Exchange endpoints live in server configuration, not the Android app.
4. Every order passes through RiskManager before reaching the exchange adapter.
5. The kill switch is database-backed so it can stop execution without redeploying code.
6. Local order records are written before the remote request to improve traceability of uncertain network outcomes.
7. An `identifier` is generated for every submitted order so later reconciliation can detect duplicates or ambiguous retries.

## cPanel execution model

The scheduler is invoked by cPanel Cron once per minute. Work must be idempotent and short-lived; no resident worker is required. Long-running market streaming is intentionally not part of the shared-hosting profile.
